ずっと知りたかった Linux -stable リリースの全て
===============================================

"-stable" ツリーに受け入れられるパッチと受け入れられないものについての規則:

- それ、もしくは等価な修正が Linux メインライン (upstream) にある。
- 明らかに正しく、テストされているものでなければならない。
- 文脈（変更行の前後）を含めて 100 行を越えてはいけない。
- Documentation/process/submitting-patches.rst の規則に従っている。
- 人々を悩ませている現実のバグの修正、もしくは単なる device ID の追加。
  前者について補足:

  - oops, ハング、データ破壊、現実のセキュリティ問題、ハードウェアの癖、
    （CONFIG_BROKEN以外の）ビルドエラー、その他「ああ、これはダメだ」
    という問題の修正。
  - ディストリビューション・カーネルのユーザーから報告された深刻な問題のうち、
    性能や応答性で顕著な影響を持つものの修正は対象になりうる。
    ただし、その類の修正は自明でなく、気づきにくいリグレッションのリスクが
    高いため、ディストリビューションカーネルのメンテナーが bugzilla 項目への
    リンクと、ユーザー視点の影響についての付加情報をつけて送付すべき。
  - どのように競合状態が発生するかの説明も一緒に書かれていない限り、
    「理論的には競合状態になる」ようなものは不可。
  - ユーザーへの利点がない「些細な」修正（スペルの修正、空白のクリーンアップなど）
    は不可。


stable ツリーにパッチを送付する手続き
-------------------------------------

.. note::

   セキュリティーパッチは、-stable のレビュー手続きではなく、
   Documentation/process/security-bugs.rst
   の手順に従うべし。

"-stable" ツリーに変更を送付する３つの選択肢:

1. メインライン向けのパッチ送付時のパッチ説明に 'stable tag' を付加する
2. stable チームに、メインラインに入っているパッチを拾うよう依頼する
3. メインラインに入っている変更と等価なパッチを stable チーム宛に送付する

以下のセクションで各々の選択肢について詳しく述べる。

`選択肢１`_ が\ **強く**\ 推奨され、最も容易でよく使われる。
`選択肢２`_ は、主として投稿時にバックポートが考慮されなかった変更向け。
`選択肢３`_ はこれら２つの代替として、古い系列に適用する際に、
メインラインのパッチに調整（例: API 変更への対応）が必要な場合向け。

選択肢２と３を使う場合、適用する stable 系列を指定することができる。
その際は、その修正か、それと等価なものが適用可能で、投稿済みであるか、より新しい
stable 系列に適用済みであることを確認する。これは、カーネルのアップグレード
に伴うリグレッション（例: 5.19-rc1 でマージされた修正が 5.10.y にバックポート
されたが、5.15.y にはされていない）の予防のため。

選択肢１
********

メインライン向けに投稿するパッチが、後日自動的に stable ツリーに取り込まれる
ためには、次のタグをサインオフ行に付ける。 ::

  Cc: stable@vger.kernel.org

未公開の脆弱性を修正する場合は、代わりに ``Cc: stable@kernel.org`` を付ける。
こちらはどこにも配送されないアドレスであり、修正が ``git send-email`` 経由で
意図せずに公開されるリスクを下げる。

このタグを持つパッチがメインラインに入ると、作者やサブシステムのメンテナー
が何もしなくても stable ツリーに適用される。

stable チームに追加の指示を送るには、シェル形式のインライン・コメントで、
任意の、もしくは事前に定義されたメモを使う。

* チェリーピックすべき前提条件となるパッチの指定::

    Cc: <stable@vger.kernel.org> # 3.3.x: a1f84a3: sched: Check for idle
    Cc: <stable@vger.kernel.org> # 3.3.x: 1b9508f: sched: Rate-limit newidle
    Cc: <stable@vger.kernel.org> # 3.3.x: fd21073: sched: Fix affinity logic
    Cc: <stable@vger.kernel.org> # 3.3.x
    Signed-off-by: Ingo Molnar <mingo@elte.hu>

  このタグ列は次の意味::

    git cherry-pick a1f84a3
    git cherry-pick 1b9508f
    git cherry-pick fd21073
    git cherry-pick <this commit>

  ただし、パッチシリーズの場合、そのシリーズに含まれるもののリストは不要。
  例: 次のパッチシリーズで、 ::

    patch1
    patch2

  patch2 が patch1 に依存する場合、patch1 が既に stable 向けにマーク済であれば
  patch1 は前提条件のリストで省略可。

* カーネルバージョンの前提条件::

    Cc: <stable@vger.kernel.org> # 3.3.x

  このタグは指定のバージョン以降の各 -stable ツリーについて::

    git cherry-pick <this commit>

  の意味を持つ。

  ただし、stable チームが適用すべきバージョンを Fixes: タグから導ける場合は
  このようなタグ付けは不要。

* パッチの適用の延期::

    Cc: <stable@vger.kernel.org> # after -rc3

* 既知の問題の指摘::

    Cc: <stable@vger.kernel.org> # see patch description, needs adjustments for <= 6.3

stable タグにはこの他に、stable チームのバックポート・ツール（例: AUTOSEL や
'Fixes:' タグを含むコミットを探すスクリプト）に無視させるバリエーションがある ::

     Cc: <stable+noautosel@kernel.org> # reason goes here, and must be present

選択肢２
********

メインラインにマージ済みのパッチであれば、stable@vger.kernel.org 宛に
パッチのサブジェクト、コミットID、適用すべき理由、適用対象のカーネルバージョン
を記したメールを送る。

選択肢３
********

上記のルールに従っていることを確認した後、適用対象のカーネルバージョンを
記載してそのパッチを stable@vger.kernel.org に送る。その際、次のように、
アップストリームのコミットIDを投稿の Changelog のコミットテキストの上部に
書く。例::

  commit <sha1> upstream.

もしくは、 ::

  [ Upstream commit <sha1> ]

投稿するパッチが（古いAPI に合わせるなどで）上流（訳註: upstream）の元の
パッチから乖離している場合、パッチの説明にその旨を明記し正当化する。

投稿後の手続き
--------------

投稿者は、パッチがキューに受け入れられると ACK が、さもなければ NAK が返される。
この応答には stable チームの都合によって数日かかることがある。

受け入れられれば、他の開発者や関係するサブシステム・メンテナーのレビューのために
、そのパッチは -stable キューに追加される。

レビューサイクル
----------------

- -stable メンテナがレビューサイクルを決めるとき、パッチはレビュー委
  員会とパッチが影響する領域のメンテナ(提供者がその領域のメンテナで無
  い限り)に送られ、linux-kernel メーリングリストにCCされる。
- レビュー委員会は 48時間の間に ACK か NAK を出す。
- もしパッチが委員会のメンバから却下されるか、メンテナ達やメンバが気付
  かなかった問題が持ちあがり、linux-kernel メンバがパッチに異議を唱え
  た場合には、パッチはキューから削除される。
- ACK を受けたパッチはリリース候補 (-rc) として再度送信され、開発者とテスター
  が試験する。
- 通常は -rc リリースは１度だが、顕著な問題があれば、一部のパッチの変更、除去、
  追加パッチのキューが行われ、-rc リリースとテストを問題が解消するまで繰り返す。
- -rc リリースへの応答は、メーリングリストに送られる "Tested-by:" のメールに
  よる。"Tested-by:" タグは集められてリリースコミットに付けられる。
- レビューサイクルが終わると、キューに入れられた検査済みのパッチからなる新しい
  -stable リリースがリリースされる。
- セキュリティパッチは、通常のレビューサイクルを通らず、セキュリティ
  カーネルチームから直接 -stable ツリーに受け付けられる。
  この手続きの詳細については kernel security チームに問い合わせること。

ツリー
------

- 完了したバージョンと進行中のバージョンのいずれについても、パッチのキューは
  ここから入手可能:

    https://git.kernel.org/pub/scm/linux/kernel/git/stable/stable-queue.git

- stable カーネルの完了してタグ付けされたリリースは、次のバージョン毎のブランチ
  から入手可能:

    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git

- stable カーネルのすべてのバージョンのリリース候補はこちらから:

    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux-stable-rc.git/

  .. warning::
     -stable-rc ツリーは stable-queue ツリーのスナップショットであり、頻繁に
     変化し、しばしばリベースされる。試験目的でのみ（例: CI システムから）
     利用すること。


レビュー委員会
--------------

 - この委員会は、このタスクについて活動する多くのボランティアと、少数の
   非ボランティアのカーネル開発者達で構成される。
